## Fixed by running it

`test/drive_bobby.rb` builds the application, opens real SQLite files into it
and asserts the observable result of every action, dialog, menu and
accelerator. It ends in `474 of 474 checks passed` / `DRIVE OK` and writes
sixteen screenshots under `tmp/shots/`. The first run of it found five things
no amount of reading had:

- I routed both the drop target and the file dialog through `Gio::Application#open`, which cannot be called from Ruby at all — ruby-gnome has no marshaller for a C array of GFile and raises `NotImplementedError: TODO: in Ruby -> GIArgument(array/C)[interface(interface)](GFile)` — so drag-and-drop and **Open...** had never opened a file. I am an idiot. Both now call `Application#open_files`, the body of the handler GIO calls for the "open" signal. Upstream: `src/gtk/widgets/drop_target.rs`, `src/gtk/dialogs/file.rs`. Port: `lib/bobby/widgets/drop_target.rb`, `lib/bobby/dialogs/file.rb`, `lib/bobby/application.rb`.
- I let the list model's rows be garbage collected. `Sqlite::RowObject` keeps its `Row` in a Ruby instance variable and ruby-gnome only weakly associates the Ruby half with the GObject, so once `Cache.model_for` returned nothing referred to them: a collection left a store of GObjects whose `#row` was `nil` — a blank table, and a segfault in the bind handler at a few hundred rows. I am an idiot. `Sqlite::Cache` keeps its `RowObject`s now and `Widgets::Content` keeps the cache. Port: `lib/bobby/sqlite/cache.rb`, `lib/bobby/widgets/content.rb`.
- I let `Window#reload` reach into a window with no database. The row-order and monospace-font preferences reload the active window, and a window in its error state has none, so changing either preference while an error was on screen raised `NoMethodError` inside the GSettings handler and took the process with it. Upstream's `window_reload` leaves with `Err` there and the caller discards it. I am an idiot. Upstream: `src/gtk/windows/window.rs`. Port: `lib/bobby/window.rb`.
- I hung the application's window bookkeeping on "destroy", and GTK4's `gtk_window_close` unmaps a window and takes it off the application **without emitting it**, so a window closed with `win.close` stayed in `Application#windows` for ever and the next file opened would have been loaded into a window nobody could see. I am an idiot. `close-request` is watched too now. Port: `lib/bobby/application.rb`.
- I left the old table behind when a window left the content state, so `win.copy-row` on an emptied window still copied from the table it used to show and the next table was appended below the one no longer on screen. I am an idiot. `show_empty_state` and `show_error_state` drop the content now. Port: `lib/bobby/window.rb`.

What still cannot be driven, and why, is in `.reports/drive-bobby.md`: a
`Gdk::FileList` cannot be constructed from Ruby, so the drop target's accepting
branch is reachable only from a real pointer drag, and `Gtk::FileDialog`'s

## About the bindings

Moved here out of `lib/bobby/sqlite/cache.rb`, where it was being used to
explain the missing paging.

- Upstream's `DatabaseCacheModel` is a `glib::Object` subclass implementing the `gio::ListModel` interface: `item(n)` fetches a 256-row page centred on `n`, caches it in a `BTreeMap`, and evicts everything further than 256 rows from `n`; `n_items()` answers `SELECT COUNT(*)` once and remembers it.
- A Ruby class **can** implement a GInterface's virtual functions, which is the assertion I had been making the other way round for three rounds without ever testing it. `include Gio::ListModel` after `type_register`, then `virtual_do_get_n_items`, `virtual_do_get_item_type` and `virtual_do_get_item`, and `Gtk::SingleSelection` and `Gtk::ColumnView` drive them. The ordering is the whole trick and it fails silently: included *before* `type_register` the GType is registered without the interface, every `g_list_model_*` call fails its `G_IS_LIST_MODEL` assertion on stderr, and the model answers 0 items rather than raising. The `virtual_do_*` methods have to come after the `include` too, because `GLib::Instantiatable.method_added` binds each one to a vfunc as it is defined (`glib2.rb:121`, `:172-177`). A registered GType name must also be at least three characters, or `type_register` raises `failed to register type`.
- The two alternatives that need no GInterface have now been run in the devShell, which does have the gems. `Gtk::SliceListModel` exists in the bindings, constructs as `Gtk::SliceListModel.new(model, offset, size)`, takes a new `offset` while live, and a `Gtk::ColumnView` accepts a `Gtk::SingleSelection` over one. Repopulating a live `Gio::ListStore` under a showing `ColumnView` — `remove_all` then `append` of a 256-row page — does not crash and leaves the vertical adjustment's value alone. Neither of them is lazy paging, and for the same reason: the scrollbar's range is the number of items in the model the view was given, so a 64-item slice makes the view describe 64 rows out of two thousand. A full-length model has to exist either way, which means one GObject per row either way. What they could still buy is lazy row *data* — a store of row objects that fetch their cells on first bind — and what stands in the way of that is the weak Ruby/GObject association recorded under *Fixed by running it*: a `RowObject` held only by the store loses its Ruby half, and a lazily filled one would come back empty. Measured against a 2,000-row table in `nix develop --command xvfb-run -a ruby`.
- `Gio::ListStore` holds GObjects only, which is what upstream's `BoxedAnyObject` is for. ruby-gnome has no `BoxedAnyObject`, so `Sqlite::RowObject` is a `type_register`ed `GLib::Object` with one attribute. That part stands.
- Upstream's paged query for a rowid table is `WHERE rowid >= offset LIMIT n`, which lines up with the row index only while the rowids are contiguous and start at zero. Whatever replaces the eager read should page with `LIMIT`/`OFFSET` rather than copy that.
- What a Flatpak manifest for this port has to do differently from upstream's, for whoever picks that up: upstream's two manifests build with meson driving cargo against `org.freedesktop.Sdk.Extension.rust-stable`, and `build-aux/dist-vendor.sh` exists only to feed `cargo --offline` inside that build. None of it builds any part of a Ruby gem. A Ruby manifest has to put Ruby itself in the sandbox — either from a runtime that already carries it or by building it as a module — and then vendor the gems the way `dist-vendor.sh` vendors crates, which for Bundler is `bundle package` writing `vendor/cache`. The gems this port needs are not pure Ruby: `sqlite3`, `gtk4` and `adwaita` all build native extensions against libraries that have to be in the sandbox too. `flatpak-builder` is not in the dev shell, so none of this has been run.
- The root bundle does not resolve on the Ruby this port supports, which is why there is no `Gemfile.lock`. `Gemfile:21` asks for `kettle-family ~> 1.3, >= 1.3.29`; `bobby-rb.gemspec` declares `required_ruby_version >= 3.4`. Every published 1.x of `kettle-family` declares `Ruby >= 4.0.0` — checked against `rubygems.org/api/v1/versions/kettle-family.json`, which lists 153 releases with that floor and 41 more at `0.2.x` with `>= 3.2.0`, so floating inside `~> 1.3` cannot lower it. Bundler on Ruby 3.4.11 answers `Because kettle-family >= 1.0.0 depends on Ruby >= 4.0.0 ... version solving has failed.` I could not run `bundle lock` for this repository at all here: the `bundle` on PATH in both the ambient shell and the dev shell is a Nix wrapper whose `BUNDLE_GEMFILE` points into the store, and it writes there rather than into the checkout. The part of this that was a real defect — that no declared test command ran — is fixed and is under *Fixed in the packaging round*.

## Deliberate divergences from upstream

Places where the port does not do what upstream does, on purpose. Each is a
located correspondence: upstream's line, then the port's. They are here, and
not only in a class comment, because this is where a reader looks for them.

- **The reload banner's button works here and is inert upstream.** Upstream sets `action_name = "app.reload"` (`src/gtk/windows/window.rs:350`) and defines no `app.reload` anywhere — `grep -rn 'reload' src/` finds the window action `win.reload` and the app action never. So upstream's banner button does nothing when pressed. The port targets `win.reload` (`lib/bobby/window.rb:241`), which exists and re-reads the file. Upstream's banner is never revealed either, so neither app shows the button today; the divergence only becomes visible the day a file monitor is written.
- **`Gtk::Application` stands in for `Adwaita::Application`.** Upstream's app is a `libadwaita::Application` (`src/gtk/lib.rs:20`). The port builds a `Gtk::Application` and calls `Adwaita.init` itself (`lib/bobby/application.rb:37-38`, `:124`), because `Adwaita::Application` is one of the two Adwaita classes the Ruby bindings cannot construct. This is the sibling of the `Adwaita::ApplicationWindow` substitution recorded above, and it costs the same thing: the Adwaita application's own initialisation, which `Adwaita.init` does by hand.
- **A tableless or missing-table file gets an error page here and no window at all upstream.** Upstream's `window_show_content_state` returns `Err("Table list empty")` / `Err("Table does not exist")` (`src/gtk/windows/window.rs:333-341`), `window_handle_open` passes the `Err` up, and `connect_open` discards it with `_ =` (`src/gtk/lib.rs:31`) — so opening a tableless file presents no window, and doing it while a window is open leaves that window untouched. The port catches both strings and renders them as the error status page's description (`lib/bobby/window.rb:296`, `:414-420`), which is a state transition upstream does not have. It is the port being more informative than the spec, and it is driven as intended at `test/drive_bobby.rb` steps 16-19.
- **The cache pages by OFFSET where upstream pages by rowid.** Upstream's `Database::rows` pages a rowid table with `WHERE rowid >= {offset} ORDER BY rowid {order} LIMIT {limit}` (`src/bobby/sqlite/row.rs:40-48`), and that only lines up with a row index while the rowids are contiguous, start at zero and are read ascending. Read newest-first, which is the default, it answers the first `limit` rows of the whole table whatever the offset — so a cache paging with it would show row 0 wherever it was asked to look, which is what a drive check caught. `Sqlite::Row.all` still carries upstream's query, because that is what upstream's `rows` is; `Sqlite::Row.page` is a second query that orders by rowid and then takes `LIMIT`/`OFFSET`, and it is what `Sqlite::Cache` pages with (`lib/bobby/sqlite/row.rb`, `lib/bobby/sqlite/database.rb`). A view or `WITHOUT ROWID` table is the same `LIMIT`/`OFFSET` query in both.
- **The toast title is markup-escaped here and raw upstream.** Upstream interpolates the copied value straight into a Pango markup string (`src/gtk/actions/win_copy_val.rs:50`), so a cell containing `<` or `&` loses characters when Pango parses the title. ruby-gnome has no binding for `g_markup_escape_text`, so the port escapes by hand (`lib/bobby/actions/win_copy_val.rb:36-43`, `:118`). Driven: a cell holding `Ada <&>` reaches the toast's title as `Ada &lt;&amp;&gt;`.
- **Upstream's dead long-copy title is ported dead.** `src/gtk/actions/win_copy_val.rs:49-53` builds `"Copied to clipboard"` for a value at or past the cutoff and then never shows it, because the `if` that picks the title and the `if` that adds the toast test the same condition. The port reproduces that, string and structure both (`lib/bobby/actions/win_copy_val.rb:33-40`, `:103-109`), so the two apps say the same thing on the day the second `if` goes.

## Fixed in the paging round

- **The whole table was read into memory before the window appeared.** `Sqlite::Cache` built a `RowObject` for every row and appended all of them to a `Gio::ListStore`, against upstream's `DatabaseCacheModel` (`src/bobby/sqlite/cache.rs`), which is a custom `gio::ListModel` answering `item(n)` from a `BTreeMap` it fills on a miss with a 256-row page at `n - 128`, then evicting every cached index further than 256 from `n`. For three rounds I recorded this as something the bindings could not do. They can: the cache is now itself a `Gio::ListModel` with upstream's two constants, upstream's page offset and upstream's guard radius, so opening a table runs one `COUNT` and one 256-row `SELECT` and scrolling runs one `SELECT` per page crossed. Port: `lib/bobby/sqlite/cache.rb`, `lib/bobby/widgets/content.rb`. The binding ordering that makes it work, and the way it fails when you get it wrong, are under *About the bindings*.
- **The feature line the port ships is true again.** `data/studio.planetpeanut.Bobby.metainfo.xml:65` carries upstream's `Scroll through tables and views of any size`, and the eager read was the gap that sentence was false of.
- **A Ruby-implemented `Gio::ListModel` aborts the process unless the view is detached first.** GTK's list-item manager asks the model for items from inside `gtk_list_base_dispose`, and a `Gtk::ColumnView` whose Ruby wrapper is freed by Ruby's garbage collector is disposed *inside the sweep* — ruby-gnome's `holder_free` calls `g_object_unref` there. GTK then calls Ruby from a GC phase and ruby-gnome allocates a Ruby Integer for the index it is marshalling, which is `[BUG] object allocation during garbage collection phase` and a `SIGABRT`. It is not a refcount problem: the vfunc's return is balanced, measured with `GLib::Object#ref_count` over fifty calls through both the model and a `Gtk::NoSelection`. `Widgets::Content#detach` sets `column_view.model = nil`, and every path that stops showing a table — `swap_content`, `drop_content`, `Window#close` and the application's `close-request` and `destroy` handlers — calls it, so the manager has nothing to ask by the time the dispose happens. Reproduced in twenty-five lines: open a 2,000-row table and `window.reload` with a full `GC.start` between reloads aborts on the first reload without the detach and survives twenty-five with it. Port: `lib/bobby/widgets/content.rb`, `lib/bobby/window.rb`, `lib/bobby/application.rb`.
- Driven against the drive's 400-row `zbig` table: the cache is empty before the first read, one read caches exactly `CACHE_PAGE_SIZE` rows starting at 0, `page_offset` is `index - 128` floored at zero, a read at row 399 pages in from 271, everything below `399 - 256` is evicted, and the cache never holds all 400 rows at once.

## Fixed in the packaging round

- **REAL cells rendered differently from upstream, everywhere they appear.** Upstream writes a REAL with `f.to_string()` (`src/bobby/sqlite/affinity.rs:51`), which is Rust's `Display for f64`: the shortest round-tripping decimal, positional, no trailing `.0`, never an exponent. `Affinity#to_s` used Ruby's `Float#to_s`, which does the trailing `.0` and does use an exponent, so a stored `1.0` read `1.0` here and `1` there, and a stored `1e300` read `1.0e+300` here and three hundred and one digits there. It reached the cell, the tooltip and the clipboard, because all three go through that one method. `Affinity#real_to_s` now takes the digits from `Float#to_s`, which is also shortest-round-trip, and only moves the decimal point, so nothing is lost through a decimal library. Five spec examples and six drive checks cover it, including the rendered label's text and the tooltip.
- **The long-copy cutoff counted characters.** Upstream's `selection.len()` (`src/gtk/actions/win_copy_val.rs:49,55`) is a Rust String's byte length; the port tested `value.length`, which is Ruby's character count, so fifty accented characters were announced here and copied silently there. It is `value.bytesize` now, and the drive copies a 47-character 94-byte value and a 48-character 96-byte one and asserts which of them gets a toast.
- **Not one of the drive's checks asserted a toast.** The toast is the only thing that tells a user a copy worked. The drive now activates both copy actions and reads the overlay back: both titles byte for byte against upstream's format strings, `timeout == 2` on each, a second activation leaving one toast rather than two, no toast past the cutoff, and `<` and `&` surviving into the title escaped. Reading them needed two things worth writing down: `Adwaita::ToastOverlay` hands nothing back once a toast is added, so `add_toast` is watched on the window's own overlay; and `class.name` is `nil` for `AdwToastWidget`, because ruby-gnome builds an anonymous Ruby class for a GType it has no binding for, so the class's printed GType name is what identifies it.
- **The metainfo advertised the port with pictures of upstream's app.** The three `<screenshot><image>` entries pointed at `raw.githubusercontent.com/hbons/Bobby`. `data/screenshots/screenshot-default.png`, `-extra-1.png` and `-extra-2.png` are now this port's own, taken by `test/drive_bobby.rb` (`tmp/shots/07-people-table.png`, `09-preferences.png`, `01-empty.png`), and the three elements point at this repository.

Upstream carries a five-line notice at the head of all 34 `.rs` files. ## Fixed in the defect round

Seven of the gaps in `.reports/component-parity.md`. Each was driven in the
devShell before and after.

- **C-05, the worst of them.** `Affinity.from_value` tested `when SQLite3::Blob`, and no read path ever produces one — that class is a write-side wrapper, and the gem hands back both `SQLITE_TEXT` and `SQLITE_BLOB` as plain `String`. So every BLOB cell was classified `TEXT`, rendered its raw bytes instead of `N BYTES`, was not dimmed, got a `TEXT <bytes>` tooltip, and when the bytes were not valid UTF-8 raised `Encoding::UndefinedConversionError` out of `Gtk::Label#text=` and aborted `bind`, so the table did not render at all. The arm now tests the encoding the gem stamps on the string (`ASCII-8BIT` is a blob, the database encoding is text) and still accepts `SQLite3::Blob` for a constructed value. Text is run through `force_encoding(UTF_8).scrub`, which is Ruby's `String::from_utf8_lossy` — upstream reads text that way and the port did not.
- **C-06.** `copy_to_clipboard` called `Gdk::Clipboard#set_text`, which ruby-gnome does not wrap; both copy actions raised. The setter is `#set`, which infers the content type from the value, so a String installs the same `text/plain;charset=utf-8` provider `gtk-rs`'s `set_text` does. Driven round trip: `set` then `read_text_async` returns the string, and `win.copy-row` on a loaded table puts the formatted row on the clipboard.
- **C-04.** `show_empty_state` and `show_error_state` each reset `top_bar_style` to `:flat`. Upstream sets Flat once in `window_new` and RaisedBorder on entering the content state, and never sets it back. The port now sets it once, in the `toolbar_view` accessor's `tap` — which also takes a styling call out of `build`.
- **C-01.** `bobby --version` exited 1 with a `Gtk::InitError` backtrace on a headless box, because `exe/bobby` did `require "bobby"` and the gtk4 gem calls `gtk_init` while being required. The half of upstream's `main()` that runs before `gui_run()` — the version line, the root refusal, the CLI — is now `lib/bobby/preflight.rb`, which requires `app`, `cli` and `log` and nothing else; `exe/bobby` runs it before it requires the rest. All four options print and exit 0 with `DISPLAY` and `WAYLAND_DISPLAY` unset. `Application#start` still calls it, so a caller holding an Application gets `main()` whole.
- **C-02.** The empty state's status page rendered the missing-image placeholder. `lib/bobby/icons.rb` stands in for `data/icons/meson.build`: it adds the shipped `data/icons` to the display's icon theme search path, which is the same registration without an install step. Both `studio.planetpeanut.Bobby` and `studio.planetpeanut.Bobby-symbolic` resolve from a checkout now; before the call neither did.
- **C-16.** `nix/Gemfile` listed `adwaita` and `gtk4` and omitted `sqlite3`, which the gemspec declares and three files require, so `require "bobby"` failed in the port's own devShell. `sqlite3` is in `nix/Gemfile` and the regenerated `nix/Gemfile.lock` and `nix/gemset.nix`; the lock was resolved conservatively, so nothing else moved. `require "sqlite3"` in the devShell now reports 2.10.2 against SQLite 3.53.3.
- **C-09.** `LICENSE.txt` was absent while the gemspec declared `GPL-3.0-or-later` and the about dialog showed `License::GPL_3_0`. Upstream's notice is ported, without the `//` Rust comment markers, and added to the gemspec's packaged metadata files.

Also: the eight comments in `lib/` that quoted an upstream deferral by the
marker word now describe it in prose instead, so a grep for stub markers over
`lib/` and `exe/` comes back empty. `Application#cli` went with C-01 — it had
no caller left.
